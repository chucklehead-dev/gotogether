# counters: grain's counter example on grist

grist's slice 1 application ([docs/grist.md](../../docs/grist.md) §8.1):
ObneyAI/grain's counter example, without float averages, written as
grist's blocks and checked against a Quint model with no annotation of
its own. grist records every block's step (each commit and committed refusal at
the store, each query on return, each effect), so what the application
writes is its decisions and folds. It runs on three tiers: grist's
simulated store (simstore), the SQL tier in simulation (grist/sqlstore
over qsql: the real tier's statements), and SQLite (a real file), each
judged by the same bindings; its clients call the app in process, over
a simulated network, or over its HTTP API (simulated on qhttp, and real
in `TestRealHTTP` and `cmd/counters`).

## The model

The model's skeleton is generated (`go run ./cmd/counters model`, from
the App's catalog: the commands' declared refusals, the processors'
declared shapes, the bank's site); its state is one tenant's log (each
tenant's trace is its own instance), the processors' checkpoints, the
batch the last step appended, the effect steps, the command ids answered
and the bank's calls as the payout saw them and as the bank applied them
(`bankPayCalls`, `bankPayRecords`). A committed
create's precondition is that its id was never answered
(`freshKey(answered, id)`), that its read set covers what its rule needs
(`createCounterNeeds`: the name's read; a runtime that loses the read is
caught at every commit), that its condition held (`conditionHolds(log,
readPos, reads)`, the read set from the step) and that the rule
(`createCounterOutcome`: `name-taken` when a counter has the name)
reaches its outcome; a refusal commits its marker too, so its id is
answered and a late duplicate cannot commit after it. `average(trigger)`
appends `averageEmits` of `log.slice(0, trigger)`; `welcomeEffect` may
repeat, under the trigger's key (`keyStable`), before `welcome(trigger,
ok)` checkpoints it with what its run reached (`atLeastOnceDone`:
notified after an ok send, `grist.failed` after three failed ones).
`payout` is at most once: its checkpoint step comes first
(`atMostOnceFirst`), its one payment after it (`atMostOnceEffect`), and
its outcome, if present, agrees with the payment (`payoutOutcome`,
`atMostOnceDone`); a lost payment or outcome is admitted. A
retirement's ok requires its `caller` (the step's, the authenticated principal) to have
created the counter (`createdBy`), `not-creator` the negation.
Hand-written are only those rules and the vals: `uniqueNames` and
`averageAsOfTrigger` are the design's (`simulate: holds`), the site
claims `everyPaymentAnswerServed` and `everyMailAnswerServed` (every
answer a caller got, unknown aside, is its dependency's served record,
field for field) are judged after the run's last settle, and the variants' vals (`once`,
`retiring`, `exactly`) are marked for their bindings. Beside them the
store's bindings judge the obligations the catalog implies (docs/grist.md
§3.3.1), generated: `everyCounterWelcomedOrFailed` and
`everyRetirementHandled`, hand-written before, were exactly
`welcomeEventuallyHandled` and `payoutEventuallyHandled` and are removed;
`everyPaymentAnswerServed` stays, stronger than the generated
`bankPayEventuallyServed` (the served record equal to the caller's, field
for field, not only of its key).

`TestMutants` builds the test binary with each mutant's overlay and runs
`TestMutant` in it. Under `-short` (every push) each claim runs at fewer
seeds, each with a miss chance under 5%, and the SQL tier's claims that
repeat a mechanism a per-push test covers run in full mode only:
`TestSQLDuplicateRequests`, `TestHTTPDuplicateRequests`, `TestHTTPTier`'s store side, `TestPayoutTwoNodes`' exactly-once half, the `silentPayout` and `anyoneRetires` mutants, `TestSQLFaithfulAtClaim1`, `TestFaithfulRetiring`, `TestPayoutAtMostOnce`'s exactly-once judgments, the `checkpointFirst` mutant, `blind`'s and
`dispatchDirect`'s SQL-tier halves, `TestSQLTier`'s Serializable half and
`TestFaithfulAtClients` (the clients' side is judged per push by
`TestDuplicateRequests` and `TestSQLTier`).

## Run it

```sh
go test -short ./...                 # every claim, at CI's seeds
go run ./cmd/counters model             # regenerate the model's skeleton and the bindings after changing a block
./run-demo.sh                        # claims 2 and 3
MUTANT=blind ./run-demo.sh         # claim 1
MUTANT=dispatchDirect ./run-demo.sh
SERVE=1 ./run-demo.sh                # cmd/counters served on SQLite, driven with curl, its steps validated
ROLLING=1 ./run-demo.sh              # a rolling restart under load, simulated and on three real pods (GR10 slice 2)
MUTANT=noDrainDelay ./run-demo.sh   # its mutants: refused tries; MUTANT=stopNodeAtSignal: an unknown payout
COUNTERS_COST=752 go test -run TestValidationCost -v .   # a run of about 1000 steps, judged
```

Judging one tenant's run (one seed, the explorer's determinism rerun
included, a loaded 4-core machine): 214 steps in 6.0 s, 999 steps in
25.3 s (`COUNTERS_COST=752`), of which the eventual val's own replay is
0.7 s and 7.1 s; the simulation itself takes well under a second.
